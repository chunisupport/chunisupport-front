# 起動時の通信と楽曲キャッシュ

## 可用性と読み込み順序

通常のページAPIは、システム状態確認と可用性ゲートの許可後に実行する。初回のメンテナンス画面・接続不能画面への切り替えを守るため、状態確認の1往復は残す。

状態確認APIは静的importで読み込み、専用チャンクの取得を挟まない。ルートのコードは `usePreloadRoute` の `preloadData: false` で状態確認と並列に先読みする。ナビゲーション・認証・プレイヤーデータのラッパーは、内側の `preload` を引き継ぐ。コンポーネントのマウントやページAPIの先行取得は行わない。個別の権限ガードで包まれた管理画面などは、従来どおりガード通過後にコードを取得する。

通常楽曲の表示では、現行スキーマ・順序・必須フィールドを満たすIndexedDBキャッシュを先に共有resourceへ反映する。更新日時を確認し、変更があれば一覧を取得して差し替える。キャッシュがない場合や強制更新時は、更新日時の応答を待たずに一覧を取得する。

- #301 の更新日時TTL・外部更新検知を維持する。先行通知を使わない呼び出し元には、鮮度検証後の結果を返す。
- 並列取得で一覧より後に確定した更新日時は、その一覧の鮮度として保存しない。未確認のキャッシュとして保存し、次回は先行表示後に再検証する。
- 背景再検証に失敗しても表示済みキャッシュを維持する。次回の利用要求で再試行する。
- CRUD後の強制更新ではキャッシュを先行表示せず、キャッシュ世代による無効化と古いリクエストの保存防止を維持する。
- メンテナンス応答は既存の可用性ストア・ゲートで処理する。

ジャンル・バージョン・全マスタには既存のセッション内メモリキャッシュがあり、通常楽曲一覧の表示はそれらの取得完了を待たない。ブラウザをまたぐ永続キャッシュは、対応する鮮度判定を用意できていないため追加していない。

## 比較検証（2026-11-01 JST）

変更前 `f7962545` と変更後の本番ビルドをローカルで静的配信し、PlaywrightとChromiumで各3回比較した。開発サーバーは使用していない。

条件は390×844、帯域1.6Mbps、RTT 150ms、CPU 4倍。HTML・JS・CSSはgzip配信し、HTTPキャッシュは無効化した。APIは2,500曲の合成データを返すモックで、固定遅延150msとgzipサイズ相当の転送遅延を付けた。Google Fontsは両方とも遮断した。2回目はIndexedDBを維持し、外部更新を発生させ、更新日時APIに追加で3秒の遅延を付けた。

| 指標（中央値） | 変更前 | 変更後 |
| --- | ---: | ---: |
| 初回 `/songs` のLCP | 4,884ms | 3,548ms |
| 初回の楽曲一覧見出し表示 | 5,048ms | 3,761ms |
| 2回目の楽曲一覧見出し表示（更新日時APIを3秒遅延） | 7,090ms | 2,409ms |

変更後はルートチャンク取得が状態確認APIと重なり、状態確認専用チャンクがなくなった。アプリコード上の待機関係は次のようになった（IndexedDB用の遅延チャンクなどは省略）。

```text
変更前: メインJS → 状態確認用JS → status → ルートJS → updated-at → songs → 表示
変更後: メインJS → (status || ルートJS) → (updated-at || IndexedDB参照 → 必要ならsongs) → 表示
キャッシュあり: status・ルートJS → IndexedDBから表示 → 背景で鮮度確認・差し替え
```

ブラウザで2回目の先行表示後に更新後の楽曲へ差し替わること、メンテナンス・接続不能時は状態確認以外の通常ページAPIを呼ばず専用画面に切り替わることも確認した。単体テストでは更新日時APIを保留し、キャッシュなしでも一覧取得が開始すること、キャッシュありでは応答前に表示できることを検証している。

この結果は合成データによるローカル比較であり、Issue #325 の本番計測値とは直接比較できない。本番API・実回線でのLCPは未計測。
